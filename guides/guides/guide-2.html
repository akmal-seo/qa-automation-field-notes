FIELD GUIDE 02 / API QUALITY

Practical API Testing Strategies for Modern Applications

A detailed look at API validation, authentication, authorization, data integrity, negative scenarios, and integration testing techniques.

INTRODUCTION

Why API Testing Matters

Application Programming Interfaces allow different software components to exchange information and coordinate business operations.

An API failure can affect multiple application features, including authentication, user registration, payment processing, reporting, and third-party integrations.

API testing helps identify problems at the service boundary without requiring every validation to pass through the graphical user interface.

1. Understand the API Contract

Before writing automated API tests, understand the endpoint's expected behavior.

Review the following:

  • HTTP methods and endpoint paths.
  • Required and optional request parameters.
  • Request body structure and supported data types.
  • Authentication and authorization requirements.
  • Expected response structures.
  • Documented status codes and error responses.
  • Business rules and data constraints.

OpenAPI specifications can provide a structured description of endpoints, schemas, parameters, and expected responses.

2. Validate Status Codes and Response Bodies

A successful HTTP status code does not necessarily mean the API returned the correct business result.

Validate the response body, required properties, data types, field values, and relevant business conditions. 

const response = await request.get('/api/users/101');

expect(response.status()).toBe(200);

const body = await response.json();

expect(body).toHaveProperty('id', 101);
expect(body).toHaveProperty('email');
expect(body).toHaveProperty('status', 'active');

This example uses Playwright's API request fixture. The expected response structure should match the actual API contract.

3. Cover Positive and Negative Scenarios

Positive tests validate expected behavior when valid requests are submitted. Negative tests evaluate how the service responds when requests contain invalid data or violate business rules.

Positive testing examples

  • Successfully creating a resource with valid data.
  • Retrieving an existing record.
  • Updating permitted fields.
  • Deleting a resource when authorized.
  • Submitting a valid search or filter request.

Negative testing examples

  • Submitting an empty required field.
  • Providing an invalid email or identifier.
  • Sending malformed JSON.
  • Using unsupported HTTP methods.
  • Providing incorrect data types.
  • Submitting duplicate or conflicting records.
  • Attempting an invalid state transition.

Verify that error responses are consistent, meaningful, and do not expose internal stack traces or sensitive implementation details.

4. Test Authentication and Authorization Separately

Authentication determines who is making a request. Authorization determines what that authenticated user is allowed to access or modify.

These are different security concerns and should be validated independently.

Authentication scenarios

  • Request without an authentication token.
  • Request with an invalid token.
  • Request with an expired token.
  • Request with a malformed authorization header.
  • Request with valid authentication credentials.

Authorization scenarios

  • Accessing a resource with the correct role.
  • Attempting restricted actions with insufficient permissions.
  • Accessing another user's private records.
  • Attempting to modify protected account properties.
  • Testing administrator and standard-user permissions.

5. Perform Boundary and Data Validation Testing

API input validation should cover more than typical valid and invalid values.

Identify the accepted boundaries for each field and test values around those boundaries.

  • Minimum and maximum permitted lengths.
  • Values immediately below and above numeric limits.
  • Null, missing, empty, and whitespace-only values.
  • Unicode and special characters.
  • Unexpected date formats and timezone values.
  • Large payloads within documented limits.
  • Duplicate identifiers and unique-field conflicts.

The expected result should come from the documented contract and business requirements rather than assumptions about how the API should behave.

6. Verify Data Integrity and State Changes

For APIs that create or modify records, validate the resulting state rather than relying only on the immediate response.

A useful create-and-retrieve scenario can follow this sequence:

  1. Submit a valid creation request.
  2. Capture the identifier returned by the service.
  3. Retrieve the newly created record.
  4. Compare its persisted values with the submitted data.
  5. Update a permitted property.
  6. Retrieve the record again and validate the update.
  7. Clean up the test record where appropriate.

This approach helps identify persistence issues, unexpected data transformations, and inconsistent service behavior.

7. Validate Idempotency and Duplicate Requests

Some operations may be retried because of network interruptions, client timeouts, or temporary service failures.

Where an API contract promises idempotency, repeated requests using the same idempotency key should not create unintended duplicate business operations.

Test repeated submissions, concurrent requests, duplicate resource creation, and the handling of conflicting updates.

8. Test Integration and Dependency Failures

Modern APIs frequently depend on databases, external services, queues, payment gateways, or other internal applications.

Test how the API behaves when a dependency becomes unavailable, responds slowly, returns invalid data, or rejects a request.

Consider:

  • Connection failures and request timeouts.
  • Unexpected upstream status codes.
  • Partial processing failures.
  • Retry and recovery behavior.
  • Duplicate event processing.
  • Data consistency across integrated services.

9. Organize API Automation for Maintainability

A structured API automation project separates endpoint interactions, request configuration, test data, authentication, and assertions. 

api-tests/
  authentication/
  users/
  products/
  orders/

helpers/
  apiClient.js
  authHelper.js
  dataFactory.js

config/
  environments.js

reports/
  execution-results/

This is an illustrative structure. Organize modules according to the size and complexity of the application.

10. Integrate API Tests into CI/CD

Automated API checks can run during pull requests, scheduled regression execution, and release validation.

Keep fast contract and critical business checks close to development workflows. Run broader integration and regression scenarios according to their execution cost and risk.

Execution reports should identify the endpoint, request context, expected result, actual response, and relevant diagnostic information without exposing credentials or sensitive data.

API Testing Checklist

  • Validate HTTP methods and endpoint behavior.
  • Verify response schemas and business values.
  • Cover positive and negative requests.
  • Test authentication and role-based permissions.
  • Cover boundary values and invalid inputs.
  • Verify database persistence and state transitions.
  • Check duplicate requests and idempotency.
  • Test integration and dependency failures.
  • Validate performance against defined requirements.
  • Include API checks in the appropriate CI/CD stages.

Conclusion

Effective API testing validates the complete service contract, including inputs, responses, security controls, data integrity, and failure behavior.

A balanced strategy combines focused functional checks, negative testing, integration validation, and automated execution. This provides stronger evidence about service quality than checking response status codes alone.
